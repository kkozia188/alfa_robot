# 运控系统架构与包职责边界

## 1. 要解决的根本问题

当前问题不是 ROS2 包数量不合适，而是三个概念长期混在一起：

1. **包的位置**被误当成了职责。为了方便调用 MoveIt，任务状态机、IK、抽离、碰撞和回放逐渐进入 `alfa_robot_moveit_config`。
2. **测试入口**绕过公开接口直接导入实现。脚本一旦验证成功，就容易被正式流程继续调用，最后形成无法删除的隐式依赖。
3. **状态发布者**和**事实负责人**没有严格区分。硬件、mock、MoveIt、回放都可能发布状态，但系统没有明确谁对“当前机器人状态”负责。

解决方式不是继续把每个函数拆成新包，而是固定依赖方向、唯一负责人和实验代码的晋升流程。

## 2. 目标架构

```text
任务上游 / 操作员
        |
        v
motion_internal_interfaces          Motion 域内稳定契约
        |
        v
robot_motion_runtime                唯一状态/场景事实 + 任务状态机
        |
        +----------------------+----------------------+
        |                      |                      |
        v                      v                      v
planning service       scene service         execution bridge
        |                      |                      |
        v                      v                      v
motion core        MoveIt/FCL adapter        mock / ros2_control / hardware
        |
        v
analytic IK / rollout / scorer

deployment：只负责选择并启动上述节点；真实硬件生命周期由外部 rt-control 域负责
tools/benchmark：只调用公开接口，生产包禁止反向依赖
alfa_robot_rerun：只读可视化 Adapter，不持有业务事实
```

## 3. 包职责

| 包或目标模块 | 唯一职责 | 允许依赖 | 明确禁止 |
| --- | --- | --- | --- |
| `motion_internal_interfaces` | Motion 域内跨包消息、服务、错误码和标识符 | ROS 基础消息 | 跨域公共接口、MoveIt 实现、硬件协议、任务脚本 |
| `robot_motion_core` | 运控纯算法的稳定数据模型与可复用实现；当前已承接 IK 候选配置、请求、结果和代价函数接口 | Eigen 等轻量数学库 | ROS node、launch、文件路径、可视化 |
| `robot_motion_scene_service` | 场景几何、附着箱、碰撞检查和场景适配 | interfaces、MoveIt/FCL adapter | IK、任务顺序、执行 |
| `robot_motion_planning_service`（目标） | 对外提供 IK、抽离和负重规划能力 | interfaces、core、scene service | 任务状态机、硬件控制 |
| `robot_motion_runtime` | 唯一事实源、任务状态机、超时、取消和任务回执 | interfaces、能力服务 | IK/RRT/FCL 实现、总线协议 |
| `alfa_robot_moveit_config` | SRDF、规划组、控制器配置和 MoveIt adapter | description、MoveIt | 任务状态机、业务顺序、实验脚本 |
| `alfa_robot_execution_bridge` | 把标准轨迹送到选定执行后端 | interfaces、控制 action | 重新规划、修改 IK、发布第二份权威状态 |
| `alfa_robot_rerun` | URDF/FK、实时关节状态和离线结果的只读可视化 Adapter | description、Rerun SDK、ROS 基础消息 | 权威状态、任务判断、算法成功判定 |
| `robot_motion_tools`（目标） | benchmark、系统测试、回放、诊断和数据分析 | 公开 interfaces | 被任何生产包依赖 |

## 4. 唯一事实源

### 4.1 机器人状态

- 硬件和 mock 发布的是关节**观测**。
- 只有 `robot_motion_runtime` 可以发布权威 `/robot_motion/state`。
- 仿真启动时允许调用一次 `/robot_motion/set_state` 固定初始状态；真实硬件模式禁止人工状态覆盖。
- 每个状态必须带 `state_id`、时间戳和来源；规划请求应记录使用的 `state_id`。

### 4.2 场景状态

- 只有 `robot_motion_runtime` 发布权威 `/robot_motion/scene`。
- `robot_motion_scene_service` 负责生成和检查几何，但不自行决定哪一版场景是当前事实。
- 每次箱墙开洞、箱体附着或释放都生成新的 `scene_id`。
- MoveIt、Rerun 和算法审计必须消费同一 `scene_id`，禁止分别重建障碍。

## 5. 调试代码晋升规则

测试和调试不应被限制，但必须经过以下四步才能进入正式运行：

1. **实验脚本**：放在 `scripts/ik_benchmark` 或未来 `robot_motion_tools`，只能调用公开服务。
2. **算法候选**：提取为无 ROS 副作用的 core，并通过确定性单元测试。
3. **能力服务**：增加稳定请求/响应、超时、取消、错误码和集成测试。
4. **任务编排**：由 `robot_motion_runtime` 调用能力服务，禁止复制算法实现。

如果一个脚本仍需要直接导入生产包的私有源码、读取工作区绝对路径或自行维护机器人状态，它就还没有资格成为正式流程。

## 6. 测试策略

- **core 单元测试**：不启动 ROS，覆盖算法输入输出和失败原因。
- **能力服务测试**：启动单个服务，使用固定 state/scene fixture 验证接口。
- **系统测试**：从 `/robot_motion/set_state`、`/robot_motion/set_scene` 和任务服务进入，检查轨迹、回执和最终状态。
- **硬件验收**：只替换 execution adapter，算法与任务接口保持不变。
- **Rerun/RViz**：作为只读观察者，不参与成功判定，也不提供规划事实。

## 7. 当前迁移顺序

1. 清理非运控/电控包和旧 MuJoCo 链路，消除无主维护代码。
2. 保持 `robot_motion_runtime` 为唯一事实源与任务状态机。
3. 已建立 `robot_motion_core` 并迁入 IK 候选公共接口；继续迁入候选排序、去重、抽离 rollout 和轨迹评分实现。
4. 新建或迁入 `robot_motion_planning_service`，承接 IK、抽离、负重规划服务。
5. 将 `alfa_robot_moveit_config` 收窄为配置与 MoveIt/FCL adapter。
6. Rerun 公共实现已集中到 `alfa_robot_rerun`；继续将 benchmark 和系统测试集中到 `robot_motion_tools`，并禁止生产代码反向依赖实验目录。
7. 按相同职责迁移到 `robot_motion_control` 仓库。

## 8. 审查门槛

新增 ROS2 包或节点前必须回答：

- 它拥有哪个唯一概念？
- 删除它后，复杂度会消失还是扩散到多个调用者？
- 它通过哪个公开接口被调用？
- 它是否产生第二份机器人状态、场景或任务事实？
- 它是不是为了测试方便而绕过现有接口？
- 如果这是实验代码，它满足了哪一级晋升门槛？

无法明确回答时，不应把代码加入正式启动链路。
