## 当前结论

## 命名契约

### 机械臂关节与连杆

当前模型采用接近新机械臂原始 URDF 的命名：

- 左臂关节/连杆：`leftjoint1` ~ `leftjoint6`
- 右臂关节/连杆：`rightjoint1` ~ `rightjoint6`
- 升降与底座：`pitch`、`turn`、`updown`

项目额外保留两个无版本语义的辅助 link：

- 左右安装基座：`left_arm_base`、`right_arm_base`
- 左右工具 TCP：`left_tool0`、`right_tool0`

这里没有继续沿用 `versioned left-arm names` / `versioned right-arm names`，避免后续每换一代机械臂就让算法、控制、仿真命名全部变成历史包袱。

### MoveIt 规划组

当前规划组统一为：

- 单臂：`left_arm`、`right_arm`
- 双臂：`dual_arm`
- 带升降轴：`left_arm_with_base`、`right_arm_with_base`、`dual_arm_with_base`
- 工具组：`left_tool_group`、`right_tool_group`

### 控制器

当前控制器统一为：

- `torso_controller`
- `dual_arm_controller`
- `left_arm_controller`
- `right_arm_controller`
- `left_arm_position_controller`
- `right_arm_position_controller`
- `all_position_controller`

### 执行接口命名

执行桥仍把对外执行层的易读关节名作为独立接口：

- 执行接口：`left_joint1` ~ `left_joint6`、`right_joint1` ~ `right_joint6`
- MoveIt/URDF 内部：`leftjoint1` ~ `leftjoint6`、`rightjoint1` ~ `rightjoint6`

这个转换由 `ros2_ws/src/alfa_robot_moveit_config/src/execution_trajectory_adapter.cpp` 承担，是当前的命名 Adapter seam。

## 当前仍需注意

### 提交边界

本轮有三类必须一起进入同一组变更，否则新模型会出现“代码能编译但资源缺失”的问题：

- 当前 mesh 资源：`ros2_ws/src/alfa_robot_description/meshes/current_robot/`
- 当前 MuJoCo 生成器：`simulation/mujoco/tools/generate_mujoco.py`
- 当前无版本命名的 ROS2 / MoveIt / MuJoCo 配置与生成结果。

历史日志、归档说明和旧 CSV 实验结果里仍可能出现旧命名，它们不是当前运行 Interface。检查当前包时以 `ros2_ws/src/`、`scripts/ik_benchmark/`、`simulation/` 的源码和配置为准，不要为了清理历史文本破坏实验追溯。

### MuJoCo 仿真资产

`simulation/mujoco/` 已同步为当前无版本命名，包括 XML 场景名、生成脚本和 Python 说明文本。

但它目前仍只是实验仿真资产，还没有升级成正式孪生 Adapter。后续如果要让 MuJoCo 成为权威孪生状态的一部分，需要补齐：

- 与 `RobotModelContract` 的模型版本校验。
- 与 `MotionSceneService` 的场景状态同步。
- 与真实执行层/Mock 执行层的状态回灌规则。

### 历史实验脚本

`scripts/ik_benchmark` 当前已经没有 `legacy versioned arm names` 残留；但它仍然是历史实验入口，后续如果继续使用，需要确认它加载的是当前安装后的 MoveIt 配置，而不是旧编译产物。

`scripts/dh_workspace` 下仍保留 `alfa_v2/v3/v4` 一类历史 URDF 对比配置。这些文件的版本号表达的是历史标定对象，不是当前运行包的 Interface；不要把它们误认为当前规划组、控制器或机器人模型命名。

## 为什么当前“全流程 demo 启动”不够稳定

现在的全流程更像一个大 demo runner，而不是稳定仿真/孪生服务，主要问题不在单个算法，而在接口深度不够：

1. **Robot state 没有唯一权威来源**
   当前很多脚本会各自假设起始关节、当前 updown、箱子状态。这样很容易出现“Rerun 里看起来对、MoveIt PlanningScene 里其实不是同一个状态”的问题。

2. **PlanningScene 是隐藏全局状态**
   箱墙、集装箱、附着箱子、临时障碍都通过 MoveIt 场景注入。只要某个 demo 没按正确顺序清场景/加场景，就会得到完全不同的碰撞结论。

3. **启动顺序和生命周期靠脚本拼接**
   现在很多流程依赖 launch 参数、sleep、临时 ROS_DOMAIN_ID、临时进程清理。它能跑实验，但不像一个长期在线的服务。

4. **参数接口过宽**
   一条 launch 命令里塞太多业务参数，说明 Module 的 Interface 太浅：调用者必须知道太多内部细节。

5. **可视化是事后回放，不是验证门槛**
   Rerun 很适合回放和审计，但目前不是权威状态源。它应该作为 Adapter 订阅孪生状态，而不是由 demo 脚本临时拼出“看起来像真实流程”的画面。

## 建议的服务化方向

### 1. RobotModelContract Module

职责：

- 提供唯一的 joint/link/group/tool 命名契约。
- 提供执行接口名和 MoveIt/URDF 名之间的转换。
- 提供模型版本、tool0、updown 范围、默认姿态等模型资产版本信息。

收益：

- 命名变化集中在一个 seam。
- 后续换机械臂不需要全仓搜索替换。

### 2. MotionSceneService Module

职责：

- 维护集装箱、箱墙、当前箱子、附着箱子的权威状态。
- 对外提供“设置场景、附着箱子、释放箱子、查询碰撞、导出快照”的小 Interface。
- MoveIt/FCL 只是它背后的一个 Adapter。

收益：

- 避免 demo 脚本各自构造碰撞口径。
- 后续替换 MoveIt 碰撞或增加几何快速碰撞时，有明确 seam。

### 3. DigitalTwinState Module

职责：

- 维护当前机器人关节状态、执行状态、任务状态、场景状态。
- 对 RViz、Rerun、执行桥、任务编排提供同一份状态。

收益：

- “真实状态”“仿真状态”“可视化状态”不再各讲各话。
- Rerun/RViz 变成订阅 Adapter，而不是流程脚本的一部分。

### 4. MotionTaskOrchestrator Module

职责：

- 负责状态机：接任务、请求 IK、请求抽离规划、请求负重规划、请求执行。
- 不直接拼 MoveIt 场景、不直接做 IK 细节、不直接画 Rerun。

收益：

- 全流程从 demo runner 变成稳定任务服务。
- 后续硬件/仿真切换只换 Adapter。

### 5. Planner Adapter 组

职责：

- IK Adapter：BioIK/KDL/后续解析解。
- Extract Planner Adapter：当前 KDL 小步抽离与横向让位。
- Loaded Planner Adapter：当前 MoveIt/OMPL 负重规划。
- Collision Adapter：当前 MoveIt/FCL，未来可替换为自研几何/FCL/Bullet。

收益：

- 算法可以持续实验，但对外 Interface 稳定。
- 一个 Adapter 出问题不会污染整条链。
