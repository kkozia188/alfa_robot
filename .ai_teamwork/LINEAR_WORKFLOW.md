# 功能开发与 Linear 进度管理规范

以功能为核心：**一项功能、一个 Issue、一条功能分支，完成后一次 PR 压缩合并。**
Linear 是正式进度记录，本地文档是协作上下文，不能互相替代。

## 1. 开工：Issue 与分支

- 先检查已有 Issue，明确目标、范围、验收、依赖、产物和负责人；不按每次提交拆 Issue。
- 创建功能 Issue，并在实际开工时设为 `In Progress`；未开工保持 `Backlog`。
- 同步目标仓库的最新开发主干，从该节点创建功能分支。主干以仓库约定为准，不固定为 `main`（例如 `alfa_robot` 使用 `alfa_v3_dev`）。
- 分支用短英文并包含 Issue ID，例如 `feature/motion-xxx-wall-transfer`；该功能所有增量提交和 review 修复均留在此分支，完成前不逐次合并主干。
- 开工前读 Issue 描述、最新评论和关联提交；不移动、覆盖或提交其他功能的未完成工作。

Issue 描述模板：

```md
目标：完成什么功能。
范围：做什么，不做什么。
验收：可检查的完成标准。
依赖：所需模型、接口、其他 Issue 或外部输入。
产物：代码、文档、测试及证据。
负责人：实际负责该功能的人。
```

## 2. 每次提交：关联并评论

- 首次提交必须关联功能 Issue；此后每个功能提交也使用 `Refs <Issue ID>` 或在 Linear 手动关联。
- 保留组织提交格式，例如 `feat(motion): 增加箱墙搬运入口`，正文写 `Refs MOTION-xxx`。
- 每个功能提交后，在同一 Issue 下追加一条 3～6 行进度评论。Git 关联不代替评论，也不假设魔法词会自动生成评论。
- 开发中不用 `Fixes / Closes / Resolves` 提前关闭 Issue；自动关联不可用时使用提交链接手动补录。
- 无关功能、维护或实验不强行挂到当前 Issue；测试须说明本机、CI、仿真或实机，不能混称。

进度评论模板：

```md
进展：本次完成内容。
证据：commit 链接、分支及可访问的产物。
验证：执行了什么，结果如何。
风险：未解决问题；无则写无。
下一步：后续工作；阻塞时说明等待谁、需要什么。
```

## 3. 完成：验收、PR、Done

- 功能达到 Issue 验收标准后，从同一功能分支发起 PR，目标为约定开发主干；PR 关联原 Issue，不为每次增量或 PR 重复建 Issue。
- PR 发起时提交最终验收评论，记录完成内容、提交/PR、测试证据及遗留；发起 PR 本身不代表 Done，等待 review 时使用团队对应状态（如 `In Review`）。
- 沿用组织 PR 模板、review、CI 和必要验收门禁；通过后 squash merge，并在最终评论中补齐合并结果和主干提交，再设为 `Done`。
- 只有确实应在合并后关闭 Issue 时才使用关闭魔法词；集成未自动变更状态时手动更新。
- 原验收之外的新算法、性能优化或探索是独立功能，另开 Issue 和分支；不要让已完成 Issue 无限承接后续方向。

最终验收评论模板：

```md
验收结论：通过 / 部分通过 / 暂不通过。
完成内容：本 Issue 范围内的功能。
证据：PR、原提交、压缩合并后的主干提交及产物。
验证：测试结果与环境；未做的验证明确列出。
遗留：不阻塞本功能验收的限制。
后续 Issue：链接；尚未创建则注明未建，不编造 ID。
```

## 4. 历史补录

- 已合并功能可补建一个 Issue；按原提交顺序逐条评论，标记“历史补录”、原日期和提交链接。
- 最终评论引用实际合并 PR 与主干提交，按原功能验收设置 Done；补录日期不冒充原开发或完成日期。
- 不重写历史、不补造魔法词、不把合并范围以外的开发中功能或测试结果纳入完成证据。
- 评论只写结论和关键证据；不贴完整终端输出。本机路径注明仅本机可用，不冒充可下载附件。
